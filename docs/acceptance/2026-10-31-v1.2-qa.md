# v1.2 可用性与稳定性验收

> 验收时间：2026-10-31 · 版本 1.2.0 · 142 工具 / 55 上游
> 环境：Linux x64，Node 22.23.4，`https://bca.davidwang.space`，模型 pi + stepfun/step-3.5-flash

## 一、结论

| 维度 | 结果 |
| --- | --- |
| 路演主路径（8 类问题） | 服务端 **100%**（40/40 请求返回正确工具与真实数据） |
| 延迟 | p50 **11.4s** / p90 **17.2s** / p95 **17.9s**；优化前最大 50s，现已降到 ≤13s |
| 服务稳定性 | 测试期间 **0 次重启**，内存稳定在 731MB（3.5G 机器） |
| 全量工具 | 零配置下 **42/142 真实跑通**；37 个按设计需要凭据或服务配置；63 个本轮未验证（原因见第五节） |

一句话：**演示路径是稳的，长尾工具还没验完。**

## 二、方法

三组独立测试，避免"只测通的那几个"：

1. **全量扫描**：用 SDK 在单进程内逐个 `invoke` 全部 142 个工具，按 schema 自动构造最小合法参数，4 路并发，单工具 45s 超时。
2. **黑盒稳定性**：对公网域名连续发 8 类问题（3 轮 24 次 + 5 轮 40 次），只走 HTTP，模拟真实访客。
3. **服务端核对**：对照 nginx 访问日志与 systemd 状态，区分"服务端失败"与"客户端网络失败"。

## 五、发现与处理

### 已修复

**Solana 全量持仓 50 秒**。首次压测时该题耗时 50s：agent 调 `solana_tokens` 未带 `mint`，遍历了该地址 3125 个 SPL 账户（大量空投垃圾币）。已在系统提示词中约束：问"某地址持有多少某代币"时必须带 `mint`。复测 **12.9s / 7.7s / 11.0s**。

### 判定为非缺陷

**`viem_logs` / `dev_forge_build` / `dev_forge_test` 在 4 路并发下超时**。单独复跑：`viem_logs` 6.4s 正常返回日志，`dev_forge_build` 22.4s 返回 `Nothing to compile`。是并发争抢公共 RPC 与本地编译资源造成的长尾，单用户场景不触发。

**`bridge_*` 九个工具报"未知 MCP 服务"**。设计如此：需要先 `bca connect dune` 之类把服务写进配置。

**`dev_slither_analyze` 报 `spawn slither ENOENT`**。未安装 slither 时的事实陈述，`bca doctor` 也会提示；可接受，但报错可以更友好（见改进项）。

### 未验证（46 + 13）

测试脚本按 schema 自动填了 `test` 这类占位值，撞在业务校验上，没有真正执行到业务逻辑。主要集中在：
EAS 编码/注册/签名（需要真实 schema 与 PrivateData）、Arweave/Walrus/Seal（需要真实 blobId 与 packageId）、x402 支付载荷、Safe 多签（需要真实 Safe 地址）、SLSA/in-toto/C2PA/OTS（需要真实证明文件）、Sign Protocol（需要合法链名）、子图（需要 key）。

这些不算通过也不算失败，建议按需补测——只测真实使用场景，不为覆盖率造数据。

## 六、改进建议

1. **`dev_forge_*` 缺 Foundry 时应快速失败**，而不是等到编译阶段才超时；现在靠 22s 的编译结果间接发现。
2. **`viem_logs` 默认参数应限制区块范围**（如最近 1000 块），避免一次拉全量。
3. **`slither` 缺失的报错**可以改成"未安装 slither，请执行 bca setup --install"，与其他工具一致。
4. 未验证的 59 个工具，建议在 `capability_list` 里标注"未验证"状态，避免被当成已验证。

## 七、路演动作：现场发行代币与 NFT

为了让"发行"这件事在台上真实可见（有交易哈希、有合约地址），体验站接了一条**本地沙盒链**，而不是主网。

### 架构

```
访客浏览器 → 体验站(4175) → pi agent
                                ├── mcp server「bca」        主网只读（BCA_ALLOW_WRITES=false）
                                └── mcp server「bca-sandbox」本地 Anvil 31337，允许写
```

两个 MCP 服务挂在同一个 agent 下，产物隔离：

| | bca（主网） | bca-sandbox（沙盒） |
| --- | --- | --- |
| 链 | Ethereum 主网 | 本地 Anvil，chainId 31337 |
| 写权限 | 关闭 | 开启 |
| 私钥 | 无 | Anvil 测试账号 0 |
| 能做什么 | 查余额、查协议、查 NFT、跨链报价 | 部署合约、发行 ERC20、铸造 NFT |
| 风险 | 无写能力 | 只作用于本机临时链，访客无法触达主网写操作 |

沙盒由 systemd `bca-anvil` 托管（`--block-time 1`），路演前用 `reset-sandbox.sh` 重置到创世状态并清空演示目录。

### 实测

| 动作 | 工具链 | 耗时 |
| --- | --- | --- |
| 发行 ERC20（STAGE / 100 万枚） | `project_init → project_run → dev_forge_deploy_local` | **25.8s** |
| 发行一枚纪念 NFT | `project_init → project_run → dev_forge_deploy_local → dev_erc721_mint_local` | **32.6s** |

产出是真实交易：合约地址、交易哈希、gas 消耗都由本地链返回，可用 `cast` 复核。

### 为了上台做的三处收敛

1. **限制 agent 的工具集**（`--exclude-tools bash,edit,write,read,glob,grep`）。第一版没有限制时，agent 会用 `ls`/`cat`/`curl` 探索环境，同一个发币任务花了 77 秒且轨迹凌乱；限制后降到 25–30 秒，轨迹只剩三步。
2. **把发行流程写成硬指令**（固定 dir、contract、from、submit），并明确禁止调用主网服务的 `project_*`（否则会报主网路径不存在）。
3. **NFT 预设改为一枚**。10 枚是逐次 mint，实测 105 秒；单枚 32 秒。

### 预设问题（体验站展示前 6 个）

1. 发行一个叫 STAGE 的代币，总量 100 万枚
2. 在沙盒链上发行一枚纪念 NFT
3. 这个代币安全吗 0xdAC17F958D2ee523a2206206994597C13D831ec7
4. ETH 现在多少钱
5. Uniswap 现在锁了多少流动性
6. Vitalik 手里有几个 BAYC
7. 从以太坊跨 0.1 ETH 到 Base 要多少钱、多久到
8. 算一下 BCA-WORKFLOW.md 的 CID

七题实测全部命中预期工具，耗时 9–33 秒。第 8 题原本是"把这句话算成 CID"，但 `content_cid` 只接受工作目录内的文件路径，字符串会让 agent 反复尝试（实测 102 秒），因此改成文件题。
