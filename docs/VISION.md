# 长期展望：让每个人都能创造自己的链上产品

> 这是一份**愿景文档**，不是功能清单。它回答两个问题：BCA 最终要做成什么，以及为什么现在做。
>
> 配套阅读：[README](../README.md)（做的是什么）· [商业模式](BUSINESS.md)（怎么活下去）· [在线文档](https://songconmaisaix31-design.github.io/blockchain-anything/)
>
> 黑客松路演可直接用第 6 节的 3 分钟口播稿。

## 1. 一句话

**链上世界缺的不是技术，是入口。**

过去十年，公链把"可信规则"这件事变得可行：资产归属、权限、分成、凭证，都可以写成代码，由网络保证执行。但要用上它，你得先成为开发者——学 Solidity、配 RPC、算 gas、处理 nonce。**技术做出来了，只有千分之一的人能碰到。**

我们认为这个门槛不该存在。BCA 要做的，是把"创造链上规则"从工程能力还原成表达能力。

## 2. 问题不在链上，在人

市面上的 Web3 工具大多只面向懂合约的开发者。"所有人都可以写合约"是技术视角——它假设用户关心的是 Solidity、RPC 和 gas 参数。

Blockchain Anything 站在用户视角：**所有人都可以创造自己的链上产品。**

| | 传统 Web3 工具 | Blockchain Anything |
| --- | --- | --- |
| 面向对象 | 懂 Solidity 的开发者 | 有想法的任何人 |
| 表达方式 | 写合约、配环境、调 RPC | 用自然语言描述想法 |
| 交付物 | 一份合约源码 | 一个可发布、可运行的链上产品 |
| 失败成本 | 编译报错、部署踩坑 | 规则先跑一遍，通过再上链 |
| 接入方式 | 逐个 SDK 集成 | 一套 MCP 工具集，任意 Agent 直接调用 |

这不是把合约编辑器包装得好看一点，而是把"写合约"这件事从用户的心智负担里拿出去。

## 3. 拐点：Agent 把"实现"这一步接走了

过去两年，变化发生在另一条线上：Agent 学会了理解意图、拆解任务、调用工具、自己纠错。

这意味着人机分工第一次可以这样切：

- **人负责"要什么"**——规则、边界、给谁用、怎么分。
- **Agent 负责"怎么做"**——查文档、写代码、跑测试、部署、验证。

而 BCA 的位置，是**这两者之间的能力层**：把链上世界的能力整理成 Agent 能直接调用、能安全使用的工具集。

一句话概括分工：**Agent 负责对话、理解与任务循环，BCA 提供工具发现、项目操作、连接管理与真实结果。**

## 4. 一个完整任务长什么样

```
描述想法  →  Agent 理解意图
          →  发现需要的链上工具      bca find
          →  生成规则并实现          bca init / build
          →  本地跑一遍真正验证      bca test
          →  核对权限与写操作边界     bca doctor
          →  钱包授权，发布上链      工作站 / 宿主钱包
```

用户只需要说一句："做 100 个 NFT，只有社群成员能 mint。"

剩下的不用他关心，但**必须让他看得懂、拦得住**：规则先在本地编译、测试、试运行，确认行为和费用，最后一步才由用户自己的钱包授权上链。合约编译、单元测试、本地链试运行全部在用户本机完成，不需要 RPC、不需要签名权限——"规则先跑一遍"是真实可用的能力，不是一句宣传语。

写操作则必须显式授权：公共链交易沿用宿主钱包的授权流程，本地一键部署仅面向明确批准的 loopback Anvil。**能力可以交给 Agent，签字权永远留在人手里。**

## 5. 这件事能长成什么

NFT 是最直观的第一个入口——它是普通人最容易理解的链上规则形式。但同一套能力可以延伸到更远的地方：

- **社群会员**：凭证即身份，权限规则写在链上，不再依赖中心化后台
- **电子票务**：可验证的发行来源与流转记录，天然防伪
- **链上游戏**：资产归属与规则公开，玩家真正拥有道具
- **多人协作**：所有权与贡献可追溯，分配规则自动执行
- **数字所有权凭证**：从内容到 AI 产出，锚定不可篡改的归属与来源

再往远看一层，是三个阶段：

| 阶段 | 谁在创造 | 形态 | 现在的进度 |
| --- | --- | --- | --- |
| **一 / 能力层** | 开发者与 Agent | 142 个工具、三个入口、一套 MCP 实现 | v1 已交付，开源可用 |
| **二 / 产品层** | 非开发者 | 说出想法 → 得到可发布、可运行的链上产品 | 流程已跑通，体验待打磨 |
| **三 / 身份层** | 人与 Agent 共同参与 | Agent 拥有可追溯的链上身份，人定的规则由 Agent 执行，全程可审计 | 设计阶段 |

第三阶段的动机很直接：当大量 Agent 开始替人行动，**谁为它的行为负责、能被谁追溯**就成了绕不过去的问题。为 Agent 分配不可篡改的链上身份，把注册信息、交互记录与经验资产锚定在链上，让 A2A（Agent-to-Agent）交互全程可追溯——这不是科幻设定，而是第一阶段工具集（`agent_*`、`sign_*`、`identity`、SLSA / in-toto / C2PA 来源验证）自然长大的方向。

这一阶段的终局是：**规则由人制定，由 Agent 执行，由链保证不可抵赖。**

## 6. 为什么是现在

三件事同时到位了，缺一件都不行：

1. **协议标准化了**。MCP 让"Agent 调用外部工具"有了统一接口。在这之前，每接一个能力都是一次定制开发。
2. **Agent 真的能干活了**。理解意图、写代码、跑测试、读报错并自我修正——这是两年前做不到的。
3. **链上基础设施足够成熟**。以太坊等多条公链的 SDK、Foundry 这样的工具链、以及公共 RPC，都到了"可以被封装"的阶段。

风口不是"Web3 又要涨了"，而是**能力供给第一次可以标准化地交给 Agent**。

## 7. 为什么是我们

不是因为我们发明了新链、新协议或新算法，而是因为**我们把这件事真的做出来了，并且诚实地标注了每一处边界**。

- **覆盖广度**：142 个工具、55 家上游，从合约开发、链上读写、代币安全到身份凭证、来源审计。
- **三个入口一套实现**：CLI、MCP、TypeScript SDK 共用同一份工具定义，终端里试通的行为，在 Agent 里、在你代码里完全一致。
- **安全边界可验证**：工具目录不授予写入权限；写操作默认关闭，需要显式开关、显式 `submit`、明确的发送地址和白名单链。
- **开源、无锁定**：MIT，自带密钥永久免费。能力层不该成为新的收费站。
- **工程诚实**：验证范围、未验证项、已知限制都写在仓库里（[验证范围](../README.md#验证范围与已知边界)、[S2 记录](../tasks/S2-progress.md)）。不把"注册了工具"说成"业务已通过"。

## 8. 已经走到哪一步

不夸大，这是当前的真实状态（2026-10-31）：

- **能装、能跑**：`bca setup` 在 Windows / Linux 上装通，MCP 握手、工具发现、真实调用已验证
- **能干活**：合约初始化 → 编译（solc 0.8.35）→ 测试，全流程真跑通过
- **能查真数据**：余额、区块、代币安全、CID、DID 解析、行情，走的是公共 RPC 与公开接口
- **能接 Agent**：市面上跑一个真实任务，8 个典型问题里 7 个命中真实工具调用，单次 8–25 秒
- **还没做到的**：账户型服务的完整业务路径、公共测试网源码上传、Windows / macOS 原生客户端 UI，都仍在验证队列里
- **还没有付费用户**：v1 是开源阶段，[商业模式](BUSINESS.md)里的定价是待验证假设

## 9. 下一步

1. **把第二阶段做实**：让完全不懂链的人，从"说出想法"到"拿到能用的链上产品"，中间不需要接触任何命令行。
2. **补齐验证缺口**：账户型服务、测试网部署、原生客户端。
3. **Agent 身份**：把 `agent_*` 与来源验证能力，扩展成可注册、可追溯的链上身份层。

## 11. 评委可能问什么

**Q：这不就是给 LLM 套一层工具调用？技术上有什么壁垒？**
壁垒不在协议，在**覆盖广度与标注质量**。142 个工具背后是 55 家上游，每一家的鉴权、参数语义、失败格式都不同；每个工具我们都标注了只读/可写、前置条件、失败语义。Agent 能不能安全地自主决策，取决于这些标注准不准，而不是取决于有没有 MCP。

**Q：为什么用户不直接让 Agent 调 viem？**
Agent 自己调 viem 需要知道用哪条链的哪个方法、参数叫什么、精度怎么处理、错误码什么意思。BCA 把这些封成带 Schema 和失败语义的工具，还能跨生态（EVM / Solana / Sui / Aptos）统一调用。跨生态这一层，自己写就是重造一遍我们做过的事。

**Q：没有付费用户，商业上怎么成立？**
开源 + 托管的 open-core：自带密钥永久免费，愿意付钱的人买"不用自己管 44 个上游密钥"。具体定价和单位经济学在[商业模式](BUSINESS.md)里，我不在这里硬报一个未验证的数字。

**Q：安全性怎么保证？"让 Agent 写合约"听起来很危险。**
三道闸：一是工具目录本身不授予写权限；二是写操作默认关闭，需要全局开关 + 单次 `submit` + 明确发送地址 + 链白名单；三是所有合约先在本地编译、测试、跑通才允许上链，签字由用户钱包完成。**能力交给 Agent，签字权留在人手里。**

**Q：现在做到什么程度了？**
v1 可装、可跑、可接 Agent，8 个典型任务 7 个命中真实工具调用。但我不会说"全部验证通过"——账户型服务、测试网部署、原生客户端仍在验证队列，这些在仓库里都写着。

**Q：为什么是你做这件事？**
因为我们既做过底层（工具封装、失败语义、写入闸门），也真的把它接到了真实 Agent 上跑通。这件事的难点不在想法，在把 55 家上游的差异磨平成一套 Agent 能用的接口——这是脏活，我们已经干完了。
